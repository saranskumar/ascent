A · Problem insight

Problem & User

User
A team member’s brother, with cerebral palsy. Observed directly. Reliable motor input is one reachable region of a phone he already owns. Speech is present but not consistently recognized. Overlapping motor + speech limits are common in cerebral palsy — not a one-off case.
Gap
TalkBack still needs swipe gestures he cannot land. Voice Access still needs speech that is not recognized. Each current system assumes one complete channel. Short clips: those tools working for a single impairment, then breaking on this combination.
Today
WhatsApp works — scroll, tap that region, send a voice note. Anything outside that set: Google Assistant after phrase-training (“call amma”), or a caregiver is called in to operate the device.
Who else
Census 2011: 2.68 crore persons with disabilities; 8% recorded multiple disabilities. A rATA study estimated 24.5% of Indians had an assistive-tech need; unaffordability was the top barrier (36.9%). MouthPad (~$1,400, US-only, dental scan), foot trackballs, and AAC hardware exist. We build for the phone already in the user’s hand.
B · Validation and learning

What we tested

Evidence
Direct observation of this user — and, through him, others with similar conditions. Not a survey. Not a persona. No written reviews yet; we will not invent them. Formal use of the built app with him is the next test, not a claim we have already run.
The test
Event assumption: “an AI agent would solve this.” We tested it against his actual workflow. He already has a small set of reliable inputs. Google Assistant — itself an AI — already fails him. The bottleneck is mapping a dense service onto that residual set, not another model.
What happened
OpenClaw added overhead, security risk, and latency. We dropped it. Zero AI. A deterministic engine ranks the page. Confirmation before anything consequential. Credibility = a named user, a real current workflow, and an architecture change that followed from that — not a completed beta.
Still open
Whether he can complete more essential-service tasks independently than with WhatsApp, Assistant, and a caregiver. That is the test that still needs him in front of the built app.
C · Solution and value

KAI — Capability Awareness Interface

Core value
Measure what this user can do, then map one task onto those residual abilities. Calibration produces a live profile. Touch, joystick, trackpad, switch-scan, and voice are composed — not offered as separate apps. Touch selects; voice, when usable, fills content. Adding voice alone is not the product.
Scope we cut
The product is the input layer. We did not build a Voice Access clone or a trained recogniser. We did not make page-parsing / an agent the core — that is further out. We did not build a full accessible phone OS in 30 hours.
Vs agents
OpenClaw, Google Astra, and NAI-style agents assume a clean instruction channel (speech or text). This user does not have one. Assistant already failed that bet. KAI is not an agent with a new skin.
Why a remote
The intended surface is the smartphone he already uses. A full on-device shell is harder to test and finish here. So the 30-hour build refines the input layer on the phone and drives a computer — phone ↔ laptop — as the way to validate input without first shipping a phone OS.
D · Product and execution

What you can try

Phone
Flutter: tap-or-hold entry, optional caregiver training, axis-gated calibration, a live profile (reach, methods, voice vocabulary, visual field, contrast). Four task shapes through four methods; touch-plus-voice on text. Confirm uses the measured method. Interrupt is always on screen.
Laptop
Playwright reads a page’s accessibility tree. A heuristic ranks navigation vs information and can act. A demo relay can connect the phone to a mock service page. No LLM in that path.
Trade-offs
Browser tree, not native OS apps. Primary surface is self-built mocks (Aperture Daily). Speech recognition is simulated on purpose so the room does not depend on a microphone. TTS / narration is not built.
Variation
Judges can change the profile. The same task reshapes — including a floor of switch-scan. That is the reliability claim: not one prepared path, one runtime.
F · Continuation

Results & what comes next

Proven
We can measure a profile and reshape the same task to it. We can rank a page without an AI agent. The assumption that AI would solve his problem did not hold.
Uncertain
Independent task completion with him on a live service. Whether real speech recognition works for him. Whether confirmation stays rare enough to trust.
Next
Put the built input layer in front of him. If speech is added, it is a hosted recognizer, not a model we train. Then ordinary websites, not only mocks. Native on-phone shell after the input layer holds.
After the event
He is the first tester. His network — people with similar conditions already known to the family — is the distribution path for feedback, not a market plan. We keep going on the devices they already have.
